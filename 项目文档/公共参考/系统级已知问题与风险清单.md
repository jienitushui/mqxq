# 系统级已知问题与风险清单

本文档汇集各功能模块中重复出现的跨模块问题，避免各深度解析文档中重复列举。各文档仅保留本模块独有的问题，跨模块问题引用本文档。

---

## 一、高危问题

### 1. 全表扫描 + Java Stream 内存聚合（反模式）

**涉及模块**: 数据大屏（教师端+管理员端）、课程监管、订单统计、首页热门课程

**表现**: `queryAllByLimit(new XxxEntity())` 查全部数据再 Java Stream 过滤/分组/统计，无 WHERE 条件限制。

**影响**: 数据量增长后将导致内存溢出和响应超时。

**正确做法**: 使用 SQL GROUP BY / COUNT / SUM 聚合查询，添加 WHERE 条件和 LIMIT 保护。

**涉及 DAO**: OrdersDao, CourseDao, UserDao, MyCourseDao, CourseViewDao, CourseHomeworkDao, HomeworkSubmissionDao, CourseCommentDao, AnnouncementsDao

---

### 2. N+1 查询（teacherName 填充）

**涉及模块**: 课程中心、首页、公告政策、我的订单

**表现**: 列表查询后逐条查询 teacherName，`course.setTeacherName(userDao.queryById(course.getTeacherId()).getName())`。

**影响**: 列表 N 条数据触发 N 次额外查询。

**正确做法**: 使用 SQL JOIN 一次查出，或 MyBatis 关联映射。

---

### 3. SQL 注入风险（${} 拼接）

**涉及模块**: 作业管理、课程学生管理、课程监管

**表现**: MyBatis XML 中 `ORDER BY ${params.orderBy}` 使用 `${}` 拼接而非 `#{}` 参数化。

**涉及文件**: `CourseHomeworkDao.xml` 的 `queryByParams` 方法，`CourseCommentDao.xml`

**正确做法**: 使用白名单校验或 MyBatis-plus 的 OrderBy 工具类。

---

### 4. 退款端点权限不足

**涉及模块**: 课程购买、我的订单

**表现**: `GET /api/alipay/refund` 位于 AliPayController 下，该控制器类级别有 `@SaCheckRole("用户")` 注解，因此需要登录且具有"用户"角色才能访问，并非完全无认证。但退款接口仅限"用户"角色访问，管理员和教师无法调用，权限设计不够灵活。文档中提及的 `POST /api/payment/refund` 端点在代码中不存在。

**影响**: 退款权限仅限学生角色，管理员无法通过此接口处理退款。

---

## 二、中危问题

### 5. 无 Redis 缓存

**涉及模块**: 课程中心、首页、公告政策、AI助手、我的订单、我的课程、数据大屏

**表现**: 高频访问的统计数据、课程列表、公告列表每次直达 MySQL 查询。

**建议**: 对低频更新高频访问的数据添加 Redis 缓存（TTL 5-10分钟）。

---

### 6. buyCount 双重递增 Bug

**涉及模块**: 课程购买、我的订单

**表现**: 支付回调 `handlePaymentSuccess` 中 `addToMyCourse` 和 `updateCourseSales` 均递增 `buy_count`，导致购买数虚高。

---

### 7. 订单时间 VARCHAR 存储

**涉及模块**: 课程购买、我的订单、数据大屏

**表现**: orders 表 `pay_time`、`create_time` 为 VARCHAR 类型，SQL 中 `DATE()` 函数对 VARCHAR 行为不确定，可能导致日期筛选失效。

**建议**: 迁移为 DATETIME 类型。

---

### 8. 物理删除（硬删除）

**涉及模块**: 用户管理、运营配置、课程监管、订单

**表现**: 所有模块的删除操作均为 `deleteById` 物理删除，无逻辑删除（status=DELETED 或 is_deleted=1），数据永久丢失无法恢复。carousel 表虽设计了 `is_deleted` 字段并在查询中过滤 `is_deleted=0`，但删除操作仍使用物理删除 `deleteById`，未通过设置 `is_deleted=1` 实现逻辑删除，is_deleted 字段实际上始终为 0。

**影响**: 误删数据无法恢复；删除时不检查关联业务数据，导致悬空引用和数据不一致。

**建议**: 全面引入逻辑删除（`is_deleted` 标记或 `status=DELETED`），删除前校验关联数据完整性。

---

### 9. 无外键约束

**涉及模块**: 运营配置、课程监管、订单

**表现**: 数据库所有表间关系（如 orders.goods_id → course.id、announcements.category_id → announcement_categories.id、user_role.user_id → user.id 等）仅靠应用层维护，无 FOREIGN KEY 约束。

**影响**: 删除父记录后子记录悬空引用，数据一致性完全依赖应用逻辑，应用层遗漏校验即产生脏数据。

**建议**: 在核心关联字段上添加 FOREIGN KEY 约束，至少在 orders.goods_id、announcements.category_id、user_role 双字段等关键位置。

---

### 10. 支付接口安全性

**涉及模块**: 课程购买、我的订单

**表现**:
- `GET /api/alipay/pay` 使用 GET 方法发起支付，URL 中暴露订单号
- 支付 URL 硬编码 IP 地址（159.75.11.181:9999）
- `SaInterceptor` 配置了 `excludePathPatterns("/api/alipay/**")`，虽然 AliPayController 类上有 `@SaCheckRole("用户")` 注解，但由于拦截器完全排除了该路径，注解级别的鉴权也不会生效，导致所有 `/api/alipay/**` 端点（包括 pay 和 refund）实际上无认证。仅 `/api/alipay/notify`（支付宝回调）确实需要排除认证，但 pay 和 refund 不应被排除

---

### 11. 前后端订单状态不一致

**涉及模块**: 课程购买、我的订单

**表现**: 后端定义 5 种状态（NOT_PAY/DONE/CANCEL/REFUND_DONE/COMMENT_DONE），前端各组件（OrderList/OrderDetail/MessageContent）各自映射了不同的状态值（PAID/CANCELLED/REFUND_PENDING/REFUNDED），`OrderConstants` 类为空未统一。

---

### 12. 公告接口认证矛盾

**涉及模块**: 首页、公告政策

**表现**: SaInterceptor 放行 `/api/public/**`，但公告 Controller 上有 `@SaCheckRole("用户")`，导致未登录用户访问公告时返回 401 而非 200。

---

## 三、低危问题

### 13. 课程搜索仅匹配标题

**涉及模块**: 课程中心、首页、AI助手

**表现**: 课程搜索 SQL 仅 `title LIKE`，不搜 description。

---

### 14. /page 与 /search 功能重复

**涉及模块**: 课程中心、首页

**表现**: `GET /api/public/course/page` 和 `GET /api/public/course/search` 接口功能完全一致。

---

### 13. 热门课程全量加载

**涉及模块**: 课程中心、首页、AI助手

**表现**: 热门课程接口加载全部已发布课程再内存排序截取，随数据增长将崩溃。

---

### 14. payOrder @Transactional 自调用失效

**涉及模块**: 课程购买、我的订单

**表现**: `OrdersServiceImpl.payOrder()` 使用 `@Transactional`，但被同类内部方法调用时 Spring AOP 代理不生效，事务无保证。

---

### 15. 退款无论 API 结果都标记 REFUND_DONE

**涉及模块**: 课程购买

**表现**: 退款代码中无论支付宝退款 API 返回成功或失败，都将订单状态设为 REFUND_DONE。退款失败时不清理 my_course 记录。

---
