# 聊天功能 - 后端实现说明

学生端 AI 助手聊天的后端实现，包括对话流程、会话接口、消息同步、数据恢复和 RAG 配置。

---

## 一、完整对话流程

### 对话流程完整梳理

#### 概述

本文档详细梳理了从用户发送消息到AI返回回答，以及消息存储、查询、恢复的完整流程。

#### 整体架构

```
用户前端
    ↓
ChatController (接口层)
    ↓
ChatService (业务层)
    ↓
ChatClient + RAG (AI处理层)
    ↓
ChatMemory (Redis存储)
    ↓
ChatMessageService (MySQL持久化)
```

#### 完整流程

### 阶段1：用户发送消息

#### 1.1 前端请求
```
POST /api/user/chat
Body: {
    "question": "有没有适合10岁孩子的编程课？",
    "sessionId": "xxx-xxx-xxx"
}
```

#### 1.2 接口层处理 (ChatController)
```java
@PostMapping(produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public Flux<ChatEventVO> chat(@RequestBody ChatDTO chatDTO) {
    return chatService.chat(chatDTO.getQuestion(), chatDTO.getSessionId());
}
```

**位置**：`src/main/java/com/jieni/mqxq/controller/user/ChatController.java`

---

### 阶段2：AI处理与RAG检索

#### 2.1 生成对话ID
```java
String conversationId = ChatService.getConversationId(sessionId);
// 格式：userId_sessionId
// 例如：1_xxx-xxx-xxx
```

#### 2.2 构建ChatClient请求
```java
this.chatClient.prompt()
    .system(promptSystem -> promptSystem.text(SYSTEM_PROMPT))  // 系统提示词
    .advisors(new QuestionAnswerAdvisor(...))  // RAG检索
    .advisors(advisor -> advisor.param(AbstractChatMemoryAdvisor.CHAT_MEMORY_CONVERSATION_ID_KEY, conversationId))  // 历史消息管理
    .toolContext(MapUtil.<String, Object>builder().put("requestId", requestId).put("conversationId", conversationId).build())  // 工具上下文
    .user(question)  // 用户问题
    .stream()
    .chatResponse()
```

**位置**：`src/main/java/com/jieni/mqxq/service/impl/chat/ChatServiceImpl.java`

#### 2.3 RAG检索流程

**配置**：
```java
SearchRequest.builder()
    .query("")                    // 使用用户问题
    .topK(10)                     // 返回最相关的10条
    .similarityThreshold(0.7)     // 相似度阈值
    .build()
```

**流程**：
```
1. 用户问题 → Embedding模型 → 向量化
2. 在Elasticsearch向量库中搜索相似课程
3. 返回最相关的课程信息
4. 注入到Prompt中，供AI参考
```

**向量库数据来源**：
- 课程发布时自动同步到向量库
- 通过`CourseVectorSyncService`管理

#### 2.4 历史消息加载

**MessageChatMemoryAdvisor自动处理**：
```
1. 从Redis读取历史消息（conversationId）
2. 将历史消息注入到Prompt中
```
> 注意：如果Redis为空，MySQL恢复不是由MessageChatMemoryAdvisor自动完成，而是由ChatSessionServiceImpl在查询历史消息时手动触发（详见阶段6）。

### 阶段3：AI生成回答

#### 3.1 流式输出
```java
.map(chatResponse -> {
    String text = chatResponse.getResult().getOutput().getText();
    outputBuilder.append(text);
    String finishReason = chatResponse.getResult().getFinishReason();
    if (StrUtil.equals("STOP", finishReason)) {
        var messageId = chatResponse.getMetadata().getId();
        ToolResultHolder.put(messageId, "requestId", requestId);
    }
    return ChatEventVO.builder()
        .eventData(text)
        .eventType(1001)  // DATA = 1001
        .build();
})
```

**返回给前端**：
- 流式数据：`eventType: 1001`（DATA）
- 参数数据：`eventType: 1003`（PARAM）
- 结束标记：`eventType: 1002`（STOP）

#### 3.2 工具调用处理

**如果AI调用了工具（如queryCourseById）**：
```
1. AI生成工具调用请求
2. 执行工具（查询课程信息）
3. 将结果返回给AI
4. AI基于结果生成最终回答
5. 工具调用结果保存到ToolResultHolder
```

> 注意：finishReason检查（"STOP"时保存messageId和requestId）已合并在上述3.1的.map()代码块中执行。

### 阶段4：消息保存到Redis

#### 4.1 自动保存（MessageChatMemoryAdvisor）

**用户消息**：
```
用户问题 → UserMessage → MessageUtil.toJson() → Redis
```

**AI回答**：
```
AI回答 → AssistantMessage → MessageUtil.toJson() → Redis
```

#### 4.2 MessageUtil.toJson()处理

**对于AssistantMessage**：
```java
1. 检查是否是MyAssistantMessage
2. 如果是，获取消息本身的params
3. 如果不是，从ToolResultHolder获取params
4. 序列化为JSON，保存到Redis
```

**Redis存储格式**：
```json
{
    "messageType": "ASSISTANT",
    "textContent": "根据您的需求...",
    "params": {
        "courseInfo_20": {
            "id": 20,
            "name": "345345",
            ...
        }
    }
}
```

**位置**：`src/main/java/com/jieni/mqxq/memory/MessageUtil.java`

#### 4.3 Redis存储结构

**Key格式**：`CHAT:{userId}_{sessionId}`

**Value格式**：Redis List，每个元素是JSON字符串

**示例**：
```
Key: CHAT:1_xxx-xxx-xxx
Value: [
    '{"messageType":"USER","textContent":"有没有适合10岁孩子的编程课？"}',
    '{"messageType":"ASSISTANT","textContent":"...","params":{...}}'
]
```

### 阶段5：消息同步到MySQL

#### 5.1 聊天完成时触发
```java
.doOnComplete(() -> {
    // 1. 从conversationId中解析提取userId
    Long userId = Long.parseLong(conversationId.split("_")[0]);

    // 2. 保存会话信息
    chatSessionService.update(sessionId, question, userId);

    // 3. 同步消息到MySQL
    syncMessagesToDatabase(sessionId, conversationId, userId, question);

    // 4. 清理生成状态
    GENERATE_STATUS.remove(sessionId);
})
```

#### 5.2 同步用户问题
```java
chatMessageService.saveMessageToDatabase(
    sessionId, 
    userId, 
    MessageTypeEnum.USER.getValue(), 
    question, 
    null
);
```

#### 5.3 同步AI回答

**从Redis读取最新消息**：
```java
List<Message> messages = chatMemory.get(conversationId, 10);
// 查找最新的ASSISTANT消息
Message latestAssistantMessage = ...;
```

**提取params**：
```java
if (latestAssistantMessage instanceof MyAssistantMessage) {
    var paramsMap = ((MyAssistantMessage) latestAssistantMessage).getParams();
    params = JSONUtil.toJsonStr(paramsMap);
}
```

**保存到MySQL**：
```java
chatMessageService.saveMessageToDatabase(
    sessionId, 
    userId, 
    MessageTypeEnum.ASSISTANT.getValue(), 
    answer, 
    params  // JSON格式的params
);
```

### 阶段6：查询历史消息

#### 6.1 接口调用
```
GET /api/user/session/{sessionId}
```

#### 6.2 查询流程 (ChatSessionServiceImpl.queryBySessionId)

**步骤1：从Redis获取**
```java
List<Message> messageList = chatMemory.get(conversationId, HISTORY_MESSAGE_COUNT);
```

**步骤2：如果Redis为空，从MySQL恢复**
```java
if (CollUtil.isEmpty(messageList)) {
    // 从MySQL恢复消息到Redis
    int restoredCount = chatMessageService.restoreMessagesFromDatabase(sessionId, conversationId);
    if (restoredCount > 0) {
        // 重新从Redis获取
        messageList = chatMemory.get(conversationId, HISTORY_MESSAGE_COUNT);
    } else {
        // 直接从MySQL返回
        return chatMessageService.queryMessagesFromDatabase(sessionId);
    }
}
```

**步骤3：转换为MessageVO**
```java
return StreamUtil.of(messageList)
    .filter(message -> message.getMessageType() == MessageType.ASSISTANT || 
                       message.getMessageType() == MessageType.USER)
    .map(message -> {
        if (message instanceof MyAssistantMessage) {
            return MessageVO.builder()
                .content(message.getText())
                .type(MessageTypeEnum.valueOf(message.getMessageType().name()))
                .params(((MyAssistantMessage) message).getParams())  // 包含params
                .build();
        }
        return MessageVO.builder()
            .content(message.getText())
            .type(MessageTypeEnum.valueOf(message.getMessageType().name()))
            .build();
    })
    .toList();
```

**位置**：`src/main/java/com/jieni/mqxq/service/impl/chat/ChatSessionServiceImpl.java`

### 阶段7：从MySQL恢复消息到Redis

#### 7.1 触发场景
- Redis数据过期
- 系统重启
- 用户重新打开会话

#### 7.2 恢复流程 (ChatMessageServiceImpl.restoreMessagesFromDatabase)

**步骤1：从MySQL查询消息**
```java
List<ChatMessage> dbMessages = chatMessageDao.selectBySessionId(sessionId);
```

**步骤2：转换为Message对象**
```java
for (ChatMessage dbMessage : dbMessages) {
    Message message = convertToMessage(dbMessage);
    messages.add(message);
}
```

**convertToMessage处理**：
```java
// 解析params
if (dbMessage.getParams() != null && !dbMessage.getParams().isEmpty()) {
    params = JSONUtil.toBean(dbMessage.getParams(), Map.class);
}

// 创建MyAssistantMessage（包含params）
return new MyAssistantMessage(
    dbMessage.getContent(), 
    Map.of(),      // properties
    List.of(),     // toolCalls
    params != null ? params : Map.of()  // params
);
```

**步骤3：保存到Redis**
```java
// 清空Redis中的旧数据
((RedisChatMemory) chatMemory).clear(conversationId);
// 批量添加消息到Redis
chatMemory.add(conversationId, messages);
```

**位置**：`src/main/java/com/jieni/mqxq/service/impl/chat/ChatMessageServiceImpl.java`

#### 关键组件说明

### 1. ChatMemory (RedisChatMemory)
- **作用**：管理聊天历史消息
- **存储**：Redis List
- **Key格式**：`CHAT:{userId}_{sessionId}`

### 2. MessageUtil
- **作用**：消息序列化和反序列化
- **功能**：
  - `toJson()`: Message → JSON字符串
  - `toMessage()`: JSON字符串 → Message

### 3. ChatMessageService
- **作用**：消息持久化和恢复
- **功能**：
  - `saveMessageToDatabase()`: 保存消息到MySQL
  - `restoreMessagesFromDatabase()`: 从MySQL恢复消息到Redis
  - `queryMessagesFromDatabase()`: 从MySQL查询消息

### 4. QuestionAnswerAdvisor
- **作用**：RAG检索增强
- **功能**：从向量库检索相关课程信息，注入到Prompt中

### 5. MessageChatMemoryAdvisor
- **作用**：自动管理历史消息
- **功能**：自动从Redis读取历史消息，注入到Prompt中

> 完整的数据恢复与同步机制（三级持久化：实时同步、定时同步、数据恢复）、异常处理策略和性能优化说明详见 [四、数据恢复与同步机制](#四数据恢复与同步机制)

#### 总结

整个对话流程涉及多个环节：

1. **消息发送**：用户 → ChatController → ChatService → AI处理
2. **RAG检索**：向量库检索相关课程信息
3. **AI生成**：基于检索结果生成回答
4. **消息存储**：Redis（实时） + MySQL（持久化）
5. **消息查询**：优先Redis，失败则从MySQL恢复
6. **数据同步**：实时同步 + 定时同步 + 按需恢复

通过多重保障机制，确保了数据的实时性、完整性和可用性。

**接口地址：** `POST /api/user/session`

```http
Authorization: Bearer {token}
```

**响应示例：**

## 三、消息同步定时任务

### 聊天消息同步定时任务说明

#### 概述

实现了每天凌晨1点自动将Redis中的聊天消息同步到数据库的定时任务功能。

#### 功能特性

1. **定时同步**：每天凌晨1点自动执行同步任务
2. **去重机制**：自动检测并跳过数据库中已存在的消息，避免重复同步
3. **批量处理**：支持批量同步多个会话的消息
4. **错误处理**：单个会话同步失败不影响其他会话的同步
5. **日志记录**：详细记录同步过程和结果

#### 数据库表结构

> chat_message 表结构详见 [公共参考-数据库表结构汇总](../公共参考/数据库表结构汇总.md#六聊天相关)

#### 实现文件

### 1. 数据库表结构
- `sql/mqxq结构.sql` - 创建chat_message表的SQL脚本

### 2. 实体类
- `src/main/java/com/jieni/mqxq/domain/entity/ChatMessage.java` - 聊天消息实体类

### 3. 数据访问层
- `src/main/java/com/jieni/mqxq/dao/ChatMessageDao.java` - 聊天消息DAO接口
- `src/main/resources/mapper/ChatMessageDao.xml` - MyBatis映射文件

### 4. 定时任务
- `src/main/java/com/jieni/mqxq/common/scheduled/ChatMessageSyncScheduledTask.java` - 定时任务实现类

#### 定时任务执行流程

```
1. 获取所有Redis中的聊天会话key（CHAT:*）
   ↓
2. 遍历每个会话
   ↓
3. 解析conversationId获取userId和sessionId
   ↓
4. 检查会话是否存在于数据库
   ↓
5. 获取数据库中已有的消息（用于去重）
   ↓
6. 从Redis获取该会话的所有消息
   ↓
7. 过滤消息（只保留USER和ASSISTANT类型）
   ↓
8. 去重（跳过数据库中已存在的消息）
   ↓
9. 转换为ChatMessage实体
   ↓
10. 批量保存到数据库
```

#### 配置说明

> 定时任务 Cron 配置详见 [公共参考-定时任务](../公共参考/系统基础设施配置汇总.md#三定时任务配置)

核心 Cron 表达式：`@Scheduled(cron = "0 0 1 * * ?")` — 每天凌晨1点执行

#### 注意事项

1. **性能考虑**：
   - 定时任务在凌晨1点执行，避开业务高峰期
   - 使用批量插入提高性能
   - 单个会话同步失败不影响其他会话

2. **数据一致性**：

## 四、数据恢复与同步机制

### 聊天消息数据恢复与同步机制说明

#### 概述

实现了完整的聊天消息数据恢复与同步机制，确保Redis和MySQL之间的数据一致性，支持数据恢复和实时同步。

#### 数据流向

```
用户发送消息
    ↓
ChatServiceImpl (实时写入Redis)
    ↓
MessageChatMemoryAdvisor (自动保存到ChatMemory/Redis)
    ↓
ChatServiceImpl.doOnComplete (异步同步到MySQL)
    ↓
MySQL数据库 (持久化存储)
    ↓
定时任务 (每天凌晨1点，补充同步增量数据)
```

#### 核心功能

### 1. Redis无数据时从MySQL恢复

**触发场景**：
- 用户重新打开会话
- Redis数据过期或被清除
- 系统重启后

**实现位置**：`ChatSessionServiceImpl.queryBySessionId()`

**流程**：
```
1. 尝试从Redis获取消息
   ↓
2. 如果Redis为空
   ↓
3. 调用ChatMessageService.restoreMessagesFromDatabase()
   ↓
4. 从MySQL查询消息并加载到Redis
   ↓
5. 重新从Redis获取消息返回
```

**代码示例**：
```java
// 1. 先从Redis中获取历史消息
List<Message> messageList = this.chatMemory.get(conversationId, HISTORY_MESSAGE_COUNT);

// 2. 如果Redis中没有数据，尝试从MySQL恢复
if (CollUtil.isEmpty(messageList)) {
    int restoredCount = chatMessageService.restoreMessagesFromDatabase(sessionId, conversationId);
    if (restoredCount > 0) {
        // 恢复成功后，重新从Redis获取
        messageList = this.chatMemory.get(conversationId, HISTORY_MESSAGE_COUNT);
    }
}
```

### 2. 消息写入Redis时同步到MySQL

**触发场景**：
- 用户发送消息后
- AI回答完成后

**实现位置**：`ChatServiceImpl.doOnComplete()`

**流程**：
```
1. 用户发送消息 → 自动保存到Redis
   ↓
2. AI生成回答 → 自动保存到Redis
   ↓
3. 聊天完成后 (doOnComplete)
   ↓
4. 异步同步用户问题和AI回答到MySQL
```

**代码示例**：
```java
.doOnComplete(() -> {
    // 同步消息到MySQL
    syncMessagesToDatabase(sessionId, conversationId, userId, question, answer, requestId);
})

private void syncMessagesToDatabase(...) {
    // 1. 保存用户问题
    chatMessageService.saveMessageToDatabase(sessionId, userId, USER, question, null);
    
    // 2. 保存AI回答（包含params）
    chatMessageService.saveMessageToDatabase(sessionId, userId, ASSISTANT, answer, params);
}
```

### 3. 定时任务补充同步

**执行时间**：每天凌晨1点

**作用**：
- 作为补充机制，确保数据一致性
- 同步可能遗漏的消息
- 处理异常情况下的数据恢复

**实现位置**：`ChatMessageSyncScheduledTask.syncChatMessagesToDatabase()`

**特点**：
- 自动去重，只同步增量数据
- 批量处理，提高效率
- 容错处理，单个会话失败不影响其他会话

#### 服务类说明

### ChatMessageService

负责消息的恢复、同步和持久化操作。

#### 主要方法

1. **restoreMessagesFromDatabase()**
   - 从MySQL恢复消息到Redis
   - 用于Redis数据丢失时的恢复

2. **saveMessageToDatabase()**
   - 异步保存消息到MySQL
   - 自动去重，避免重复保存

3. **queryMessagesFromDatabase()**
   - 从MySQL查询消息列表
   - 用于Redis恢复失败时的降级方案

#### 数据同步策略

### 实时同步（主要机制）

**时机**：消息写入Redis后立即同步

**优点**：
- ✅ 实时性高，延迟最小
- ✅ 数据一致性好
- ✅ 用户体验好

**缺点**：
- ⚠️ 依赖业务代码调用
- ⚠️ 异步执行，可能失败

### 定时同步（补充机制）

**时机**：每天凌晨1点

**优点**：
- ✅ 可靠性高，作为补充保障
- ✅ 可以修复遗漏的同步
- ✅ 批量处理，效率高

**缺点**：
- ⚠️ 有延迟，不是实时同步
- ⚠️ 资源消耗相对较大

### 数据恢复（按需机制）

**时机**：Redis无数据时自动触发

**优点**：
- ✅ 自动恢复，用户无感知
- ✅ 保证数据可用性
- ✅ 无缝切换

#### 使用场景

### 场景1：用户重新打开会话

```
1. 用户打开会话
   ↓
2. 查询历史消息
   ↓
3. Redis中没有数据
   ↓
4. 自动从MySQL恢复
   ↓
5. 加载到Redis
   ↓
6. 返回消息给用户
```

### 场景2：系统重启

```
1. 系统重启，Redis清空
   ↓

   ↓

   ↓

```

### 场景3：Redis数据过期

```
1. Redis数据过期被清除
   ↓
2. 用户访问会话
   ↓
3. 自动从MySQL恢复
   ↓
4. 数据重新加载到Redis
```

#### 数据一致性保证

### 1. 去重机制

- **实时同步**：通过内容检查，避免重复保存
- **定时同步**：通过内容集合对比，只同步新消息

### 2. 幂等性

- 重复操作不会产生错误
- 可以安全地多次执行同步

### 3. 容错处理

- 单个消息同步失败不影响其他消息
- 单个会话同步失败不影响其他会话
- 异步执行，不影响主流程

#### 性能优化

### 1. 异步处理

- 消息保存到MySQL采用异步方式
- 不阻塞主业务流程

### 2. 批量操作

- 定时任务使用批量插入
- 减少数据库交互次数

### 3. 按需恢复

- 只在需要时从MySQL恢复
- 避免不必要的数据库查询

#### 监控和日志

### 日志记录

- **恢复操作**：记录恢复的消息数量
- **同步操作**：记录同步的消息数量
- **错误信息**：记录失败原因和堆栈

### 关键日志示例

```

成功恢复 10 条消息到Redis: sessionId=xxx

========== 开始同步聊天消息到数据库 ==========
成功: 5 个会话, 失败: 0 个会话, 总计同步: 50 条消息
```

#### 注意事项

### 1. 数据量考虑

- 每个会话最多恢复10000条消息
- 可根据实际情况调整

### 2. 性能影响

- 恢复操作会查询数据库，可能有一定延迟
- 建议在低峰期执行定时任务

### 3. 数据一致性

- Redis和MySQL可能存在短暂不一致
- 定时任务确保最终一致性

### 4. 错误处理

- 恢复失败时，直接从MySQL返回数据
- 同步失败时，记录日志，下次定时任务重试

#### 总结

通过实时同步、定时同步和数据恢复三种机制，确保了Redis和MySQL之间的数据一致性：

聊天服务使用的 RAG 检索参数（ChatServiceImpl.java）：

- **Embedding模型**：`text-embedding-v3`（阿里云通义千问）
- **向量维度**：`1024`
- **自动初始化**：`initialize-schema: true`（启动时自动创建索引结构）

### 2. RAG Advisor配置 (ChatServiceImpl.java)

```java
// 设置RAG查询，返回最相关的课程信息
.advisors(new QuestionAnswerAdvisor(
    vectorStore, 
    SearchRequest.builder()
        .query("")                    // 查询关键词（空字符串表示使用用户问题）
        .topK(10)                     // 返回最相关的10条结果
        .similarityThreshold(0.7)     // 相似度阈值，只返回相似度>0.7的结果
        .build()
))
```

**配置说明**：
- **QuestionAnswerAdvisor**：Spring AI提供的RAG增强器
- **vectorStore**：向量库实例（自动注入）
- **query**：查询关键词（空字符串表示使用用户问题，实际运行时QuestionAnswerAdvisor会自动替换）
- **topK**：返回最相关的K条结果（设置为10）
- **similarityThreshold**：相似度阈值（设置为0.7，过滤低相关性的结果）

### 3. VectorStore Bean配置

VectorStore由Spring AI自动配置，无需手动创建Bean。配置基于`application.yml`中的`spring.ai.vectorstore.elasticsearch`配置。

**自动配置流程**：
1. Spring AI检测到Elasticsearch配置
2. 自动创建`ElasticsearchVectorStore`实例
3. 根据配置初始化向量库结构
4. 注入到需要的地方（如`ChatServiceImpl`）

#### RAG工作流程

### 1. 用户发送问题

```java
public Flux<ChatEventVO> chat(String question, String sessionId) {
    // 用户问题：question
    // 会话ID：sessionId
}
```

### 2. RAG检索阶段

```java
.advisors(new QuestionAnswerAdvisor(vectorStore, SearchRequest.builder()
    .query("")                      // 实际查询时会使用用户问题作为query
    .topK(10)
    .similarityThreshold(0.7)
    .build()))
```

**QuestionAnswerAdvisor的工作流程**：
1. 将用户问题转换为向量（使用Embedding模型）
2. 在向量库中搜索相似度最高的文档
3. 将检索到的课程信息注入到Prompt中
4. AI基于检索到的信息生成回答

### 3. 向量库数据来源

向量库中的课程数据由 `CourseVectorSyncService` 管理，通过实时同步和定时任务同步保证与课程数据的一致性。完整同步机制（实时同步触发点、定时任务配置、同步规则、文档格式）详见 [向量库同步机制说明](../公共参考/向量库同步机制说明.md)。

向量化内容包含课程标题、描述、价格、课时、时长、购买数等属性，文档ID格式为 `course_{courseId}`。

#### 配置参数详解

### SearchRequest参数

| 参数 | 说明 | 当前值 | 建议值 |
|------|------|--------|--------|
| query | 查询关键词 | "" | 实际查询时使用用户问题 |
| topK | 返回结果数量 | 10 | 根据数据量调整（5-20） |
| similarityThreshold | 相似度阈值 | 0.7 | 0.5-0.8，越高越严格 |

**注意**：
- `query("")` 在配置时为空，实际运行时QuestionAnswerAdvisor会使用用户问题作为查询关键词
- `topK(10)` 返回最相关的10条结果，兼顾检索覆盖面和效率
- `similarityThreshold(0.7)` 过滤低相关性结果，确保注入Prompt的课程信息与用户问题高度相关

### Embedding配置

| 配置项 | 说明 | 当前值 |
|--------|------|--------|
| model | Embedding模型 | text-embedding-v3 |
| dimensions | 向量维度 | 1024 |

**模型说明**：
- `text-embedding-v3`：阿里云通义千问的Embedding模型
- 支持最大1024维向量
- 适合中文文本的向量化

#### 优化建议

### 1. 调整topK值

根据课程数据量，可以适当调整topK值：

```java
// 如果课程数量较少（<50），可以适当增加
.topK(15)

// 如果课程数量较多，建议保持或减小
.topK(10)  // 只返回最相关的10条
```

**优势**：
- 减少不相关信息干扰
- 提高检索效率
- 降低Token消耗

### 2. 使用动态查询

当前配置中`query("")`为空，QuestionAnswerAdvisor会自动使用用户问题。如果需要自定义查询逻辑，可以：

```java
// 方式1：直接使用用户问题
SearchRequest.builder()
    .query(question)  // 使用用户问题作为查询
    .topK(10)
    .similarityThreshold(0.7)
    .build()

// 方式2：基于用户问题构建更复杂的查询
String enhancedQuery = buildEnhancedQuery(question);
SearchRequest.builder()
    .query(enhancedQuery)
    .topK(10)
    .similarityThreshold(0.7)
    .build()
```

### 3. 调整相似度阈值

根据实际检索效果，可以调整相似度阈值：

```java
SearchRequest.builder()
    .query(question)
    .topK(10)
    .similarityThreshold(0.7)  // 只返回相似度>0.7的结果
    .build()
```

- 阈值越高，返回的结果越精准，但可能遗漏部分相关结果
- 阈值越低，返回的结果越多，但可能包含不太相关的结果

### 4. 优化向量库数据

确保向量库中的数据质量：
- 定期同步课程数据
- 清理无效或过期的课程
- 优化课程描述文本的质量

#### 常见问题

### 1. 为什么topK设置为10？

**原因**：课程数据量适中，设置为10可以在保证检索覆盖面的同时，避免不相关结果干扰AI回答。

**说明**：注意项目中`EmbeddingController`（测试端点）使用了`topK=999`以检索全部数据，但这与聊天服务无关。聊天服务的RAG配置使用`topK=10`和`similarityThreshold(0.7)`。

### 2. 为什么query为空字符串？

**原因**：QuestionAnswerAdvisor会自动使用用户问题作为查询关键词，配置时不需要指定。

**说明**：这是Spring AI的默认行为，Advisor会在运行时自动处理。

### 3. 如何提高检索准确性？

**方法**：
1. 优化课程描述文本
2. 调整topK值
3. 调整相似度阈值（当前为0.7）
4. 优化Embedding模型参数

### 4. 向量库数据如何更新？

详见 [向量库同步机制说明](../公共参考/向量库同步机制说明.md)，包含实时同步和定时任务同步两种机制。

#### 总结

聊天服务的 RAG 配置核心要点：

1. **RAG Advisor**：使用 `QuestionAnswerAdvisor` 进行检索增强，自动将检索结果注入 Prompt
2. **检索参数**：topK=10，similarityThreshold=0.7，确保检索到高相关性的课程信息
3. **向量库与数据同步**：使用 Elasticsearch 存储课程向量，同步机制详见 [向量库同步机制说明](../公共参考/向量库同步机制说明.md)

整个 RAG 流程是自动化的，Spring AI 会自动处理向量化、检索和注入过程，开发者只需要配置好参数即可。
